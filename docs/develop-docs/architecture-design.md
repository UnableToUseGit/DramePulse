# 架构设计

## 1. 层级划分

```text
┌──────────────────────────────────────────────┐
│ 体验层：1. 播放器渲染 2. 即时交互机制 3. 用户行为采集 │
└──────────────────────────────────────────────┘
┌──────────────────────────────────────────────┐
│ 业务层：1. 高光点识别与下发 2. 交互内容生成与下发 3. 策略更新 │
└──────────────────────────────────────────────┘
┌──────────────────────────────────────────────┐
│ 数据层：重要数据持久化（内容数据、高光资产、行为日志等） │
└──────────────────────────────────────────────┘
```

## 2. 各层职能

### 2.1 体验层

**负责：** 模拟短剧 App 的端上体验，包括播放器基础能力、即时互动渲染和用户行为采集。该层根据业务层下发的互动方案，在视频播放到指定高光点时展示低摩擦交互入口，并将用户的播放、点击、关闭、回看、拖拽等行为上报至业务层。

**不负责：**

1. 判断高光点；
2. 生成互动选项；
3. 计算互动策略；
4. 长期存储行为数据。

### 2.2 业务层

**负责：** 系统核心逻辑，包括高光点识别、互动方案生成与下发、用户行为统计和策略更新。该层将短剧内容转化为结构化高光资产，再根据高光语义和历史反馈生成前端可渲染的互动方案，并基于用户行为持续更新高光点分数和互动选项。

**不负责：**

1. 具体 UI 渲染；
2. 视频播放器控制；
3. 原始数据的底层存储实现。

### 2.3 数据层

**负责：** 关键数据持久化，包括短剧内容数据、高光资产数据、互动方案数据、用户行为事件数据以及统计与策略数据。数据层为业务层提供稳定的数据读写能力，使系统能够形成从内容理解到端上互动再到反馈优化的完整闭环。

**不负责：**

1. 判断高光点；
2. 生成互动选项；
3. 渲染客户端 UI；
4. 解释用户行为含义。

---

## 3. 模块契约设计

本章在系统层级划分与各层职能的基础上，进一步定义各层内部核心模块的职责边界、输入输出与协作关系。

本阶段的设计目标不是进入代码级实现细节，而是明确模块之间的协作契约，使前端、后端与算法开发能够并行推进。

系统整体分为三层：

- **体验层：** 负责播放、交互渲染与用户行为采集；
- **业务层：** 负责高光识别、互动方案生成、行为统计与策略更新；
- **数据层：** 负责关键数据持久化与查询。

系统中最核心的三个跨层数据对象为：

- **Highlight Asset：** 高光资产，回答“哪里值得互动”；
- **Interaction Plan：** 互动方案，回答“如何与用户互动”；
- **User Event：** 用户行为事件，回答“用户如何反馈”。

---

### 3.1 体验层模块契约

体验层面向用户，负责模拟短剧 App 的端上观看体验。该层根据业务层下发的互动方案，在视频播放到指定高光点时渲染低摩擦交互入口，并采集用户在播放和互动过程中的行为数据。

体验层不负责高光识别、互动选项生成和策略计算。

---

#### 3.1.1 播放器基础模块

**模块职责**

播放器基础模块负责提供短剧观看的基础能力，是所有互动机制的承载容器。

其核心职责包括：

1. 视频播放；
2. 暂停与继续；
3. 进度条拖拽；
4. 当前播放时间监听；
5. 视频播放状态管理；
6. 高光点进度条标记。

该模块需要持续监听视频播放时间，并判断当前是否接近某个高光点或处于某个互动触发窗口。

**输入**

- `video_id`：视频 ID；
- `interaction_plan`：业务层下发的互动方案；
- `highlight_markers`：高光点时间标记。

**输出**

- `current_time`：当前播放时间；
- `playback_state`：播放状态；
- `seek_event`：用户拖拽进度条事件；
- `highlight_enter_event`：进入高光点窗口事件。当视频播放进入某个高光点的互动窗口时，由播放器模块产生，用于通知互动渲染模块展示对应交互。

**MVP 实现方式**

MVP 阶段可以基于 HTML5 video 实现基础播放能力，并通过 `timeupdate` 事件监听当前播放时间。

高光点可以先以静态标记形式显示在进度条上。

**不负责事项**

1. 不判断哪些片段是高光点；
2. 不生成互动内容；
3. 不计算互动策略；
4. 不长期保存播放行为。

---

#### 3.1.2 即时互动渲染模块

**模块职责**

即时互动渲染模块负责将业务层下发的互动方案渲染为端上的可视化交互体验。

它不负责决定“展示什么互动”，只负责根据 Interaction Plan 执行渲染。

核心职责包括：

1. 在指定时间触发互动入口；
2. 渲染弹幕投票、情绪表达、再看一遍等互动形式；
3. 接收用户点击、长按、滑动等交互动作；
4. 展示互动后的即时反馈；
5. 控制互动组件的出现、消失和展示时长；
6. 尽量避免遮挡关键剧情区域。

**输入**

- `interaction_plan`：互动方案；
- `current_time`：播放器当前时间；
- `playback_state`：播放状态。

**典型 Interaction Plan 示例**

```json
{
  "interaction_id": "i_001",
  "highlight_id": "h_001",
  "trigger_time": 42.0,
  "interaction_type": "danmaku_poll",
  "question": "女主这波怎么样？",
  "options": [
    {
      "option_id": "o_001",
      "text": "太争气了",
      "danmaku_text": "女主太争气了！"
    },
    {
      "option_id": "o_002",
      "text": "爽到了",
      "danmaku_text": "这波爽到了！"
    }
  ],
  "feedback": {
    "type": "poll_result",
    "show_ratio": true,
    "show_resonance_text": true
  }
}
```

**输出**

- `interaction_exposure_event`：互动曝光事件；
- `option_click_event`：用户点击选项事件；
- `interaction_dismiss_event`：用户关闭互动事件；
- `feedback_shown_event`：反馈展示事件。

**MVP 实现方式**

MVP 阶段优先实现一种主交互形式：弹幕投票。

基础流程：

```text
高光点触发问题卡片 → 用户选择选项 → 展示投票比例与弹幕共鸣反馈
```

后续可以扩展：

- 情绪脉冲；
- 剧情预测；
- 角色应援；
- 再看一遍；
- 剧情同款标签。

**不负责事项**

1. 不生成投票问题；
2. 不生成选项文案；
3. 不计算投票比例；
4. 不决定选项排序；
5. 不判断用户行为对策略的影响。

---

#### 3.1.3 用户行为采集模块

**模块职责**

用户行为采集模块负责在客户端记录用户的播放行为和互动行为，并将事件上报至业务层。

该模块是反馈闭环的入口。

采集行为分为两类。

**播放行为**

- `pause`：暂停；
- `resume`：继续播放；
- `seek_forward`：向前拖动进度条；
- `seek_backward`：向后拖动进度条；
- `rewatch_segment`：反复观看某片段；
- `watch_complete`：完成播放。

**互动行为**

- `interaction_exposure`：互动入口曝光；
- `option_click`：点击互动选项；
- `interaction_dismiss`：关闭互动入口。

**输入**

- 用户播放操作；
- 用户互动操作；
- 当前播放时间；
- 当前 `video_id` / `highlight_id` / `interaction_id` / `option_id`。

**输出**

统一输出 User Event：

```json
{
  "event_type": "option_click",
  "user_id": "u_demo_001",
  "video_id": "v_001",
  "highlight_id": "h_003",
  "interaction_id": "i_003",
  "option_id": "o_002",
  "client_time": 45.2,
  "timestamp": 1710000000,
  "extra": {
    "device": "mobile_web",
    "interaction_type": "danmaku_poll"
  }
}
```

**MVP 实现方式**

MVP 阶段可以使用匿名用户 ID，例如：

- `u_demo_001`
- `u_demo_002`

事件上报可以通过 `POST /api/events` 发送到后端。

**不负责事项**

1. 不做长期事件存储；
2. 不做复杂统计；
3. 不计算 CTR、关闭率、回看率；
4. 不更新互动策略。

---

### 3.2 业务层模块契约

业务层是系统核心逻辑所在，负责将短剧内容转化为高光资产，将高光资产转化为互动方案，并根据用户行为持续更新策略。

---

#### 3.2.1 高光点识别模块

**模块职责**

高光点识别模块负责从短剧视频、字幕和元信息中识别可能激发用户表达欲的剧情高光点。

它识别的对象不是普通视频片段，而是具有互动价值的剧情事件。

该模块需要回答：

1. 这里是不是高光？
2. 高光发生在什么时间段？
3. 属于什么高光类型？
4. 可能激发用户什么情绪？
5. 情绪强度有多高？
6. 是否适合触发互动？

**输入**

- `video_id`：视频 ID；
- `video_metadata`：视频元信息；
- `subtitle_segments`：字幕片段；
- 可选：关键帧、音频特征、评论先验、人工标注。

字幕输入示例：

```json
[
  {
    "start": 38.0,
    "end": 41.2,
    "text": "你根本不知道他是谁。"
  },
  {
    "start": 41.3,
    "end": 45.0,
    "text": "他就是顾氏集团真正的继承人。"
  }
]
```

**输出**

输出 Highlight Asset 列表：

```json
{
  "highlight_id": "h_001",
  "video_id": "v_001",
  "start_time": 38.0,
  "end_time": 46.0,
  "highlight_type": "身份揭露",
  "emotion": "震惊",
  "intensity": 0.92,
  "summary": "男主真实身份曝光，反派震惊。",
  "reason": "前文一直铺垫男主被轻视，此处身份反转带来强爽点。",
  "confidence": 0.88
}
```

**MVP 实现方式**

MVP 阶段优先采用：字幕解析 + LLM 结构化识别 + 人工校验。

流程为：

```text
字幕切段
  ↓
候选高光召回
  ↓
LLM 判断高光类型、情绪和强度
  ↓
输出 Highlight Asset
  ↓
人工快速校验
  ↓
入库
```

**后续增强方向**

1. 引入关键帧辅助判断；
2. 引入音频强度、BGM、语气变化；
3. 引入镜头切换和特写检测；
4. 引入评论/弹幕先验；
5. 构建人工标注验证集，评估准确率与召回率。

**不负责事项**

1. 不生成具体互动 UI；
2. 不决定前端展示形式；
3. 不统计用户反馈；
4. 不根据用户反馈直接修改策略。

---

#### 3.2.2 互动方案生成与下发模块

**模块职责**

互动方案生成与下发模块负责将高光资产转化为前端可直接渲染的互动方案。

这是连接“内容理解”和“即时互动”的关键模块。

该模块需要决定：

1. 这个高光点适合哪种互动形式？
2. 是情绪表达，还是观点表达？
3. 应该展示什么问题？
4. 应该提供哪些选项？
5. 选项如何排序？
6. 用户点击后展示什么反馈？
7. 是否展示群体共鸣数据？

**输入**

- Highlight Asset；
- 历史用户行为统计；
- 互动模板库；
- 策略配置。

**输出**

输出 Interaction Plan：

```json
{
  "interaction_id": "i_001",
  "highlight_id": "h_001",
  "video_id": "v_001",
  "trigger_time": 38.0,
  "expire_time": 46.0,
  "interaction_type": "danmaku_poll",
  "question": "这波反转你怎么看？",
  "options": [
    {
      "option_id": "o_001",
      "text": "卧槽反转了",
      "danmaku_text": "卧槽反转了！",
      "rank": 1
    },
    {
      "option_id": "o_002",
      "text": "爽到了",
      "danmaku_text": "这波爽到了！",
      "rank": 2
    }
  ],
  "feedback": {
    "type": "poll_result",
    "show_ratio": true,
    "resonance_text_template": "你和 {ratio}% 的观众一样选择了「{option}」"
  }
}
```

**MVP 实现方式**

MVP 阶段可以采用规则 + LLM 生成结合：

- 高光类型 = 身份揭露 → 生成震惊/反转类选项；
- 高光类型 = 打脸反杀 → 生成爽感/支持类选项；
- 高光类型 = 甜蜜撒糖 → 生成心动/磕到了类选项；
- 高光类型 = 冲突爆发 → 生成站队/观点类选项。

初期可使用固定模板。

情绪型：

```text
这波什么感觉？
[爽到了] [气死了] [磕到了]
```

观点型：

```text
你站谁？
[站女主] [站男主]
```

行动型：

```text
这一幕要不要再看？
[再看一遍] [继续看]
```

**后续增强方向**

1. 根据用户反馈动态调整选项排序；
2. 根据高光类型自动选择互动形式；
3. 根据评论语料生成更口语化的弹幕选项；
4. 根据用户画像做个性化下发；
5. 支持剧情预测、角色应援、剧情同款标签等扩展互动。

**不负责事项**

1. 不负责前端具体动画实现；
2. 不负责用户事件采集；
3. 不直接写入原始行为日志；
4. 不处理视频播放控制。

---

#### 3.2.3 用户行为统计模块

**模块职责**

用户行为统计模块负责接收体验层上报的用户行为事件，并将其聚合为可用于分析和策略更新的统计指标。

该模块将原始事件转化为业务指标。

**输入**

输入 User Event：

```json
{
  "event_type": "option_click",
  "user_id": "u_demo_001",
  "video_id": "v_001",
  "highlight_id": "h_003",
  "interaction_id": "i_003",
  "option_id": "o_002",
  "client_time": 45.2,
  "timestamp": 1710000000
}
```

**输出**

输出统计结果：

```json
{
  "highlight_id": "h_003",
  "interaction_id": "i_003",
  "exposure_count": 100,
  "click_count": 62,
  "dismiss_count": 8,
  "replay_count": 17,
  "click_rate": 0.62,
  "dismiss_rate": 0.08,
  "replay_rate": 0.17
}
```

选项统计：

```json
{
  "option_id": "o_002",
  "exposure_count": 100,
  "click_count": 46,
  "click_rate": 0.46
}
```

**MVP 实现方式**

MVP 阶段可以采用简单实时统计或准实时统计。

每次事件上报后：

1. 保存原始事件；
2. 更新对应 highlight / interaction / option 的计数；
3. 计算点击率、关闭率、回看率；
4. 将结果写入 stats 表。

**核心统计指标**

- `exposure_count`：互动曝光次数；
- `click_count`：互动点击次数；
- `dismiss_count`：互动关闭次数；
- `replay_count`：回看次数；
- `click_rate`：点击率；
- `dismiss_rate`：关闭率；
- `replay_rate`：回看率；
- `option_click_rate`：选项点击率。

**不负责事项**

1. 不判断策略应该如何变化；
2. 不生成新的互动方案；
3. 不修改前端展示；
4. 不负责高光点识别。

---

#### 3.2.4 策略更新模块

**模块职责**

策略更新模块负责根据用户行为统计结果更新高光点分数、互动选项排序和互动触发策略。

该模块使系统具备持续优化能力。

它需要回答：

1. 哪些高光点被用户验证为有效？
2. 哪些高光点可能是误触发？
3. 哪些互动选项更受用户欢迎？
4. 哪些互动形式打扰用户？
5. 下一次应该如何调整展示策略？

**输入**

- Highlight Asset；
- Interaction Plan；
- 用户行为统计结果；
- 策略规则。

**输出**

- `updated_highlight_score`；
- `updated_option_rank`；
- `updated_interaction_plan`；
- `strategy_log`。

示例：

```json
{
  "highlight_id": "h_003",
  "old_score": 0.82,
  "new_score": 0.91,
  "reason": "该高光点回看率较高，用户反馈强烈"
}
```

选项排序更新：

```json
{
  "interaction_id": "i_003",
  "options": [
    {
      "option_id": "o_002",
      "text": "爽到了",
      "old_rank": 2,
      "new_rank": 1
    },
    {
      "option_id": "o_001",
      "text": "太争气了",
      "old_rank": 1,
      "new_rank": 2
    }
  ]
}
```

**MVP 实现方式**

MVP 阶段可以使用简单规则：

- 高回看率 → 提升高光点分数；
- 高关闭率 → 降低触发强度；
- 某选项点击率高 → 下次优先展示；
- 某互动持续被关闭 → 减少展示或降低优先级。

示例公式：

```text
updated_score =
0.5 * model_confidence
+ 0.2 * click_rate
+ 0.2 * replay_rate
- 0.1 * dismiss_rate

option_score =
0.7 * option_click_rate
+ 0.3 * base_score
```

**后续增强方向**

1. A/B 测试不同互动文案；
2. 针对不同高光类型学习不同策略；
3. 引入用户画像进行个性化下发；
4. 训练模型预测互动转化率；
5. 使用多臂老虎机等在线策略优化方法。

**不负责事项**

1. 不采集原始用户事件；
2. 不渲染前端 UI；
3. 不直接操作播放器；
4. 不重新识别视频内容。

---

#### 3.2.5 Story Q&A 辅助服务

Story Q&A 辅助服务属于业务层的可选在线能力，用于回答用户在当前观看进度内提出的剧情问题。它基于已入库的字幕、帧分析和剧集摘要做 RAG 检索，并按照 `series_id`、`current_episode` 和 `current_time` 过滤资料，避免向用户暴露后续剧情。

该服务对外提供 `/api/story-qa/ask`、`/api/story-qa/ingest` 和 `/api/story-qa/collections`。它不替代 `Highlight Asset`、`Interaction Plan` 或 `User Event`，也不负责高光识别、互动方案生成、用户事件统计或策略更新。

MVP 阶段该能力作为演示增强项存在。没有配置 OpenAI-compatible API Key 和 Chroma 存储时，核心播放、互动和事件链路仍应可独立运行。

LightRAG 可作为 Story Q&A 的可选后端，通过 `STORY_QA_BACKEND=lightrag` 启用。该模式加载离线构建好的 LightRAG working directory，保持 `/api/story-qa/*` 对外接口不变；知识图谱抽取仍属于离线流程，不进入在线 API 路径。

---

#### 3.2.6 观看助手语音输入

观看助手语音输入属于体验层输入方式和业务层辅助接口的组合能力。用户在播放器内点击助手面板的麦克风按钮后，前端录制一段短语音并上传到 `POST /api/watch-assistant/transcribe`；后端只负责把音频转写成文本，前端再把转写文本提交给 `POST /api/watch-assistant/act`，复用已有意图解析、剧情问答和播放器控制逻辑。

该能力不新增高光资产、不生成互动方案，也不改变 `User Event` 核心类型。由语音触发的播放控制事件继续通过 `/api/events` 上报，并在 `extra` 中标记 `input_mode: "voice"`、`transcript`、`asr_confidence` 和 `audio_duration_ms`。

MVP 阶段语音录制限制为短指令，建议 10 秒以内。没有麦克风权限、转写失败或没有听清时，前端保留文本输入作为降级路径，视频播放不应被打断。

### 3.4 模块协作流程

#### 3.4.1 内容处理流程

```text
内容数据管理模块
  ↓
高光点识别模块
  ↓
高光资产管理模块
  ↓
互动方案生成与下发模块
  ↓
互动方案管理模块
  ↓
即时互动渲染模块
```

对应解释：

1. 系统读取视频和字幕；
2. 业务层识别高光点；
3. 高光点作为 Highlight Asset 入库；
4. 业务层根据高光资产生成 Interaction Plan；
5. Interaction Plan 入库；
6. 体验层请求并渲染 Interaction Plan。

---

#### 3.4.2 在线互动流程

```text
播放器基础模块
  ↓
即时互动渲染模块
  ↓
用户行为采集模块
  ↓
用户行为事件管理模块
  ↓

  ↓
策略更新模块
  ↓

  ↓

```

对应解释：

1. 用户观看短剧；

3. 前端展示互动入口；
4. 用户完成低摩擦表达；
5. 客户端上报用户行为；
6. 数据层保存原始事件；
7. 业务层统计行为指标；
8. 策略更新模块调整高光分数和选项排序；
9. 下一次前端获取到更新后的互动方案。

### 3.5 MVP 阶段实现边界

MVP 阶段需要优先保证完整链路跑通，而不是追求每个模块都做到最复杂。

**必须实现**

1. 播放器基础能力；
2. 弹幕投票互动渲染；
3. 用户点击与播放行为采集；
4. 字幕驱动的高光点识别；
5. 互动方案生成；
6. 用户事件保存；
7. 基础统计；
8. 简单策略更新；
9. 高光点和互动方案持久化。

**可以简化**

1. 高光点可以先由 LLM + 人工校验生成；
2. 用户 ID 可以使用匿名 demo ID；
3. 策略更新可以先用规则实现；
4. 数据库可以先使用 SQLite；
5. 弹幕投票先支持两到三个选项；
6. 前端交互先支持点击，不必一开始支持长按、滑动、连点。

**暂不实现**

1. 真实大规模用户系统；
2. 复杂推荐算法；
3. 完整模型训练闭环；
4. 原生 App；
5. 支付和真实电商交易；
6. 个性化用户画像；
7. 大规模实时流处理。

### 3.6 本章总结

模块契约设计的核心目标是明确系统内部各模块的职责边界。

本系统的核心协作关系可以概括为：

- 体验层负责渲染互动和采集行为；
- 业务层负责识别高光、生成互动方案和更新策略；
- 数据层负责沉淀内容、高光、互动、行为与统计数据。

其中，Highlight Asset、Interaction Plan 和 User Event 是贯穿三层的核心数据对象。通过这三个对象，系统能够形成从内容理解到端上互动，再到用户反馈与策略优化的完整闭环。
