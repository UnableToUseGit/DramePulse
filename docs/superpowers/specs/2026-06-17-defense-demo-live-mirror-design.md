# 复赛答辩演示台设计说明

## 1. 背景

复赛答辩不适合继续使用传统静态 PPT。DramePulse 的优势在于“播放链路内的即时互动闭环”，所以更合适的表达方式是一个可交互、带动画、可现场操作的 HTML 演示台。

答辩时需要同时完成两件事：

1. 把系统闭环讲清楚；
2. 让评委看到真实 iPhone 上的实时操作。

因此，本方案不把演示页当作普通展示文稿，而是当作“答辩控制台 + 实机镜像窗口 + 讲解编排器”。

## 2. 目标

本演示台的目标是：

1. 用一个本地 HTML 页面承载整场答辩；
2. 提供全局悬浮入口，随时打开手机实机窗口；
3. 在页面内展示项目架构、数据流、互动闭环和关键结果；
4. 现场直接操作真实 iPhone，避免只看录屏；
5. 保留备用回放方案，降低现场不稳定风险。

## 3. 结论

技术上可行，但**不能只靠浏览器本身直接读到 iPhone 屏幕**。必须引入一个本地镜像桥接层。

推荐结论是：

```text
本地 HTML 演示台
  -> 全局悬浮入口
  -> 打开实机窗口
  -> 实机窗口显示来自 Mac 的 iPhone 实时镜像
```

其中：

- HTML 负责交互、动画和讲解节奏；
- Mac 负责承接 iPhone 镜像采集；
- iPhone 负责真实操作；
- 备用回放负责兜底。

## 4. 推荐方案

### 4.1 主方案

主方案采用“HTML 控制台 + 本地镜像桥接 + 实机操作”。

现场流程是：

1. 打开本地 HTML；
2. 页面右侧始终保留一个全局悬浮入口；
3. 点击入口后，弹出一个实机演示窗口；
4. 窗口内显示 iPhone 实时画面；
5. 在 iPhone 上完成真实点击、滑动、播放、互动；
6. HTML 页面同步展示当前讲解章节和系统状态。

### 4.2 为什么推荐

- 真实感最高；
- 评委能直接看到产品形态和操作路径；
- 演示节奏可控；
- 可以把“讲解”和“实机”分离，避免串场混乱。

## 5. 备选方案

### 5.1 录屏回放兜底

当实时镜像不稳定时，切换到预录制的实机操作视频。

优点：

- 稳定；
- 可提前剪好节奏；
- 不怕现场网络波动。

缺点：

- 真实感弱于实时操作；
- 不能即时改动演示路径。

### 5.2 纯网页模拟

只用浏览器模拟手机页面，不接真实 iPhone。

不推荐作为主方案，因为它无法满足“必须展示真实 iPhone 实时操作”的目标，只能当内部预演工具。

## 6. 架构边界

### 6.1 演示台

演示台是一个本地运行的 HTML 页面，负责：

- 分章节讲解；
- 动画化展示系统闭环；
- 控制弹窗、浮层和过场；
- 打开实机镜像窗口；
- 显示备用入口。

### 6.2 镜像桥接层

镜像桥接层运行在 Mac 上，负责把 iPhone 画面带进网页可见范围。

这个层不做业务逻辑，只做画面传输和状态恢复。

### 6.3 实机设备

iPhone 只负责真实运行项目 App 和真实交互，不被网页远程控制。

这意味着：

- 网页只负责“展示和讲解”；
- iPhone 负责“真实操作”；
- 两者通过镜像关系连接，而不是控制关系。

## 7. 风险与约束

1. 纯浏览器无法直接抓取 iPhone 屏幕，必须依赖 Mac 上的本地桥接工具。
2. 实时镜像会受连接方式、系统权限和窗口切换影响。
3. 答辩现场最好准备一键切换到备用回放。
4. 演示台的动画不能抢过内容本身，重点仍然是闭环和效果。

## 8. 验收标准

这套方案成立的最低标准是：

1. 本地 HTML 页面可独立打开；
2. 悬浮入口始终可见；
3. 点击后能弹出实机演示窗口；
4. iPhone 操作能在窗口中实时看到；
5. 备用回放可快速切换；
6. 整体演示不依赖传统 PPT。

## 9. 结论

这条路线是可行的，且比静态 PPT 更适合 DramePulse 的展示重点。

接下来应继续把它拆成两个部分：

1. 演示台 HTML 的信息架构和动效脚本；
2. Mac 上的 iPhone 实时镜像接入方式和兜底机制。
