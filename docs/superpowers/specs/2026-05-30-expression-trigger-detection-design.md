# Expression Trigger Detection 设计记录

## 1. 背景

本设计记录用于收敛 DramePulse 算法分支的高光点识别方向。

此前算法尝试把“剧情上的转折点”作为用户表达欲的代理变量，例如反转、信息揭露、关系变化、价值跃迁等。但这个假设不够准确。用户愿意表达的时刻并不总是剧情结构发生变化的时刻，也可能来自表演、角色魅力、吐槽、剧终评价等。

因此，算法目标需要从“剧情高光点识别”调整为更贴近产品目标的：

```text
识别用户愿意用低摩擦动作表达即时反应的时刻。
```

本文将这类时刻统一称为 `Expression Trigger`。

## 2. 核心定义

`Expression Trigger` 指视频时间轴上的一个时间点或短时间窗口，用户在该处很可能愿意通过不打断观看的低摩擦动作表达即时反应。

它不是普通剧情片段，也不等同于剧情转折点。一个触发点成立的最低标准是：

```text
用户愿意点击一个轻量表达入口，例如“爽到了”“震惊”“磕到了”“看哭了”“笑死”“太帅了”。
```

不要求用户愿意停下来发弹幕或评论，因为打字本身摩擦高，会中断短剧观看。也不把“有情绪波动”作为唯一标准，因为这个标准过于抽象，难以稳定评估。

剧情触发点尤其要识别“情绪释放点”，而不是单纯识别“事件让观众产生情绪”。有效的剧情触发通常存在：

```text
铺垫/压抑/期待/误导 -> 当前转折/揭晓/推进/兑现 -> 情绪释放
```

例如“反派欺负主角”多数时候只是铺垫；“主角在被压制后抓住机会反击”才更可能是 `爽到了` 的触发点。

## 3. 概念收敛

本设计只引入一个主实体：`Expression Trigger`。

它包含三个字段维度：

```text
Why  -> source_type，表达欲从哪里来
What -> primary_expression，用户主要想表达什么
How  -> interaction_mode，前端应如何低摩擦承接表达
```

三者不是三套并列分类体系，而是同一个触发点的三个属性：

- `source_type` 决定算法主要依赖什么信号识别该点；
- `primary_expression` 决定互动文案、反馈语气和统计口径；
- `interaction_mode` 决定前端渲染形态。

当前验证闭环阶段先让冷启动 LLM 只负责判断 `source_type` 和 `primary_expression`，暂不让 LLM 选择 `interaction_mode`。算法内部会为兼容现有输出结构填充默认交互形态，后续由前端设计和 Interaction Plan 生成阶段统一决定具体承接方式。

示例：

```json
{
  "trigger_id": "et_demo_ep01_001",
  "video_id": "demo_ep01",
  "cue_time": 42.3,
  "source_type": "plot",
  "primary_expression": "爽到了",
  "interaction_mode": "single_tap",
  "setup": "女主此前被反派压制和羞辱。",
  "turning_point": "女主抓住证据当众反击反派。",
  "expression_release": "前面的压抑在反击时释放，观众自然想表达解气。",
  "confidence": 0.86,
  "reason": "该点不是单纯冲突，而是压抑后的打脸释放点。"
}
```

## 4. 表达欲来源

第一版将表达欲来源收敛为四类。

### 4.1 剧情触发

用户被剧情信息、人物关系、冲突结果或情绪释放触发。

典型场景：

- 反转；
- 悬念揭晓；
- 打脸爽点；
- 反杀；
- 甜蜜撒糖；
- 危机升级；
- 情绪释放。

典型表达：

```text
爽到了、震惊、磕到了、看哭了
```

这类最适合冷启动识别。输入可以是视频、字幕和元数据，不应依赖弹幕。

冷启动 LLM 输出剧情触发点时，需要同时给出三个结构化解释字段：

- `setup`：当前点之前建立了什么劣势、压抑、期待、误导、关系张力或情感压力；
- `turning_point`：当前点发生了什么反击、兑现、揭晓、关系推进、重逢、牺牲或情感突破；
- `expression_release`：前面积累的什么情绪在当前点释放，为什么用户会在这里点击表达。

如果模型只能说明“这个情节让观众产生某种情绪”，但说不出前面的铺垫和当前释放，则第一版应跳过该点。

### 4.2 表演触发

用户被台词、行为、表情、节奏或表演方式触发。

典型场景：

- 搞笑台词；
- 夸张行为；
- 魔性动作；
- 尴尬但上头的表演；
- 角色反应形成笑点或吐槽点。

典型表达：

```text
笑死、绷不住、离谱、好抓马、他急了、这演技
```

这类主观性强，大模型直接判断不稳定。第一版更适合依赖弹幕峰值、情绪词和高赞弹幕识别；视频帧可以作为辅助确认，不作为主判断来源。

### 4.3 角色魅力触发

用户被角色外貌、造型、气质、眼神、苏感、可爱感或反差萌触发。

典型表达：

```text
好帅、太美了、老婆、老公、姐姐杀我、这个眼神、太可爱了
```

这类同样主观，且容易受到观众偏好影响。第一版不建议让大模型在冷启动时独立判断“帅”“美”“可爱”。更可靠的做法是利用弹幕中的直接表达信号，再结合视频中的人物特写或造型亮相做辅助解释。

### 4.4 剧终评价触发

这是价值判断和站队表达中的一个稳定子类。

普通剧情中的站队、道德判断、该不该原谅等表达需要长上下文和观众立场，第一版不强行完整解决。但剧集结尾或大结局处，用户常常会评价整部剧的质量，适合单独规则化处理。

典型表达：

```text
好剧、烂尾、没看够、上头、结局离谱、太短了
```

典型互动：

```text
这部剧你怎么评价？
[上头好剧] [有点烂尾] [没看够]
```

这类触发点不一定是剧情高光，而是生命周期场景，应通过剧集尾部、大结局标记、标题描述和弹幕内容共同识别。

## 5. 识别信号定位

算法设计需要区分“表达欲来源”和“证据来源”。

可用证据包括：

- 视频文件：表情、动作、镜头、人物特写、氛围；
- 字幕：剧情语义、冲突内容、人物关系、关键信息；
- 弹幕：真实观众表达欲的弱标签；
- 视频元数据：标题、简介、剧集信息、是否大结局等背景先验。

第一版建议采用三条通道：

```text
内容理解通道：
视频 + 字幕 + 元数据 -> 剧情触发表达点

观众反应通道：
弹幕时间峰值 + 弹幕语义 -> 表演触发、角色魅力、吐槽点，也可校准剧情触发点

生命周期规则通道：
剧尾 / 大结局 / 追更末尾 -> 剧终质量评价互动
```

## 6. 冷启动原则

弹幕是很好的用户表达信号，但不能成为线上推理的唯一核心，因为新短剧或低热度短剧存在冷启动问题。

因此第一版应明确两种模式：

```text
Cold-start mode:
视频 + 字幕 + 元数据 -> 预测剧情触发表达点

Evaluation / enhancement mode:
视频 + 字幕 + 元数据 + 弹幕 -> 验证、校准、补充表达点
```

其中：

- 剧情触发类必须支持冷启动；
- 表演触发和角色魅力触发优先由弹幕增强发现；
- 剧终评价由生命周期规则稳定触发；
- 弹幕可用于构造弱标签、评估算法结果和校准 prompt。

## 7. 交互形态关系

现有文档中曾将弹幕投票作为主要交互形式。实际讨论后需要调整：弹幕投票只适合有明显分歧或选择的场景，不适合作为所有表达点的默认交互。

短剧节奏快，用户不应被迫阅读多个相似选项。交互形态应由表达意图决定：

| 场景 | 推荐 interaction_mode | 说明 |
| --- | --- | --- |
| 单一强情绪，如爽、笑、磕、帅 | `single_tap` | 一个明确表达按钮即可 |
| 情绪强度需要持续表达 | `hold_burst` 或 `repeat_tap` | 适合爽点、应援、笑点 |
| 观点分歧、站队、选择 | `stance_poll` | 适合双选或少量多选 |
| 剧终质量评价 | `finale_rating` | 适合 2 到 3 个评价选项 |

因此，高光点成立不再要求“能自然生成 2 到 3 个投票选项”。更准确的标准是：

```text
该时刻有清晰的主表达欲，并能被一个低阅读成本、不中断播放的交互动作承接。
```

## 8. 与现有契约的关系

当前仓库已有 `Highlight Asset`、`Interaction Plan`、`User Event` 三个核心契约。`Expression Trigger` 可以作为算法内部概念，也可以映射回现有契约。

建议映射关系：

```text
Expression Trigger -> Highlight Asset
source_type -> highlight_type 的上层来源解释
primary_expression -> emotion 或新增 expression 字段
interaction_mode -> 交给 Interaction Plan 生成阶段使用
cue_time -> trigger_time 的主要依据
```

第一版可以不立刻改 JSON Schema，而是在算法输出中保留现有字段，同时通过文档和 prompt 将“高光点”定义修正为“表达触发点”。

## 9. 非目标

第一版不解决以下问题：

- 不构建完整用户画像；
- 不训练复杂推荐模型；
- 不要求弹幕投票覆盖所有高光点；
- 不强行让大模型判断颜值或笑点；
- 不把弹幕密集度直接等同于高光点；
- 不把所有剧情转折都视为表达触发点。

## 10. 推荐第一版范围

第一版算法应优先实现：

1. 剧情触发表达点的冷启动识别；
2. 弹幕增强通道，用于发现表演触发、角色魅力和吐槽点；
3. 剧终评价规则；
4. 输出统一的 `Expression Trigger` 风格字段；
5. 将结果转换为现有 `Highlight Asset`，供后续互动方案生成和播放器使用。

第一版评估标准应围绕：

- 识别出的点是否真的适合低摩擦表达；
- 是否能说明用户主要想表达什么；
- 是否能解释该点来自剧情、表演、角色魅力或剧终评价；
- 是否能避免把普通剧情转折误判成表达触发点；
- 是否能在无弹幕情况下产出可用的剧情触发点。
