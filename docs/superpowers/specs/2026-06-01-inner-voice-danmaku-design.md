# 心里话弹幕交互设计

## 1. 背景

短剧高光点里，用户经常会在一瞬间产生一句很具体的“心里话”：

```text
她终于怼回去了
他这句真的太狠了
这俩绝对有事
别误会她啊
我就知道要反转
```

传统弹幕要求用户点击输入框、组织语言、打字、发送。这个流程在短剧高节奏观看场景里成本太高，用户往往还没发出来，剧情已经过去了。

心里话弹幕的目标是：系统在高光点附近只给一句精准的待发送弹幕，用户觉得“这就是我想说的”，就用一个轻推手势把它发出去。

## 2. 方案定位

第一版采用 **输入按钮旁边的待发送弹幕草稿**。

它不是投票，不是多选弹幕，也不是输入框自动补全。系统只给一句，用户只有两个选择：

```text
觉得准 -> 轻推发送
没感觉 -> 不操作，草稿自然消失
```

核心体验：

```text
剧情高光点到达
-> 弹幕输入按钮旁边浮出一句心里话草稿
-> 用户轻推草稿
-> 草稿变成真实弹幕进入弹幕轨道
-> 原位置消失，播放不中断
```

这个设计借用用户已经熟悉的弹幕输入入口，让用户理解“这是系统帮我写好的待发送弹幕”，而不是突然出现的新玩法。

## 3. 出现位置

第一版把待发送弹幕放在 **弹幕输入按钮旁边**。

选择原因：

- 和“发送弹幕”的用户心智最一致；
- 不需要额外解释；
- 不占用屏幕中心剧情区域；
- 不和右侧点赞、评论、分享操作栏竞争；
- 比悬浮在画面中间更克制，更像播放器原生能力。

如果当前播放器没有显式弹幕输入按钮，第一版需要在底部播放器信息区附近增加一个轻量弹幕入口。待发送草稿应依附在这个入口旁边，而不是孤立漂浮。

位置原则：

- 位于底部剧情信息区上方或同层附近；
- 避开进度条和底部 tab；
- 避免遮挡字幕；
- 不遮挡右侧操作栏；
- 草稿宽度受控，长句应截断或提前生成更短文案。

## 4. 草稿形态

待发送弹幕应像一条“已经写好的弹幕”，而不是按钮或卡片。

建议样式：

- 半透明深色胶囊；
- 白色正文；
- 右侧或尾部有轻微推出提示；
- 可以带小的弹幕图标或发送方向暗示；
- 不使用大面积高亮，不做卡片阴影堆叠。

示例：

```text
[弹幕图标] 她终于怼回去了  ↗
```

文案长度建议：

```text
6 到 14 个中文字符优先
最多不超过 18 个中文字符
```

原因是它需要在移动端底部区域可读，同时推出后能作为普通弹幕自然飘过。

## 5. 推出手势

第一版使用 **轻推发送**，不使用点按发送。

原因：

- 推出比点击更像“把这句话发出去”；
- 可以降低误触；
- 动作有记忆点；
- 和普通输入框点击行为区分开。

推荐手势：

```text
从草稿胶囊上轻轻向上或右上推
```

选择向上或右上，而不是单纯向左，是因为草稿位于输入入口附近，用户大拇指更容易完成上推。推出后，系统可以自动把弹幕接入正常弹幕轨道。

手势规则：

- 拖动距离超过阈值后触发发送；
- 未超过阈值则草稿回弹；
- 发送后当前草稿立即进入 completed 状态；
- 同一个高光点不重复展示同一句草稿；
- 草稿展示期间，用户仍可正常暂停、seek 或忽略它。

建议阈值：

```text
纵向或斜向拖动距离 >= 28px
```

具体数值可在真机体验中调整。

## 6. 动画

推出动画要表达“草稿变成弹幕”，不做礼物特效。

建议流程：

```text
用户按住草稿并上推
-> 胶囊跟随手指移动，并轻微拉伸
-> 达到阈值后草稿脱手
-> 草稿快速抬升到弹幕轨道高度
-> 样式从待发送胶囊过渡为普通弹幕
-> 弹幕以正常速度从右向左飘过
-> 输入按钮旁边恢复空状态
```

动画原则：

- 总时长短，建议 600ms 到 900ms；
- 不暂停视频；
- 不清空普通弹幕；
- 不出现满屏粒子；
- 反馈要让用户确认“已发送”，但不能盖过剧情。

可以在发送瞬间增加很轻的反馈：

```text
已发出
```

这条反馈应小而短，展示不超过 800ms。

## 7. 文案生成原则

心里话弹幕成败取决于文案准不准。

第一版文案原则：

- 像真实观众会发的弹幕；
- 贴合当前剧情，不只贴情绪标签；
- 语气短、口语化；
- 不像剧情总结；
- 不像运营文案；
- 不包含攻击性、低俗或不适合展示内容；
- 不泄露后续剧情；
- 不生成多句供用户选择。

差的例子：

```text
女主此刻完成了情绪反击
该剧情体现了人物关系变化
观众对此处会产生强烈共鸣
```

好的例子：

```text
她终于怼回去了
别再误会她了
这句一出来我真受不了
他看她的眼神不对劲
我就知道要反转
```

## 8. 数据输入

第一版可以先使用本地 fixture 或前端配置，不强制接后端生成。

建议最小结构：

```ts
type InnerVoiceDanmakuCue = {
  cueId: string;
  videoId: string;
  highlightId: string;
  triggerTime: number;
  durationSec: number;
  text: string;
  danmakuTrack?: number;
};
```

示例：

```json
{
  "cueId": "voice_case1_ep01_001",
  "videoId": "case1_ep01",
  "highlightId": "h_case1_ep01_001",
  "triggerTime": 38.0,
  "durationSec": 4.0,
  "text": "她终于怼回去了",
  "danmakuTrack": 2
}
```

后续接入后端时，可以作为新的互动类型，例如：

```text
inner_voice_danmaku
```

第一版不立即修改共享 schema，避免在交互体验未验证前扩大契约变更。

## 9. 事件采集

第一版至少在前端本地记录：

```text
inner_voice_exposure
inner_voice_send
inner_voice_dismiss
```

事件关键字段：

- `video_id`
- `highlight_id`
- `cue_id`
- `text`
- `client_time`
- `timestamp`
- `send_gesture`

如果后续接入后端，`inner_voice_send` 可以同时生成一条用户弹幕，复用当前已有的：

```text
POST /api/videos/{video_id}/danmaku
```

## 10. 前端组件边界

建议新增独立目录：

```text
apps/player-demo/src/inner-voice-danmaku/
  types.ts
  cues.ts
  scheduler.ts
  gesture.ts
  InnerVoicePrompt.tsx
  InnerVoiceDanmakuLayer.tsx
```

职责划分：

- `types.ts`：定义 cue、状态和事件；
- `cues.ts`：第一版本地 demo cue；
- `scheduler.ts`：根据当前播放时间找到可展示草稿；
- `gesture.ts`：判断轻推阈值和回弹/发送状态；
- `InnerVoicePrompt.tsx`：渲染输入按钮旁边的待发送草稿；
- `InnerVoiceDanmakuLayer.tsx`：处理草稿发出后的弹幕轨道动画。

`PlayerPage` 负责传入当前播放时间、播放状态、视频 ID 和弹幕入口位置，不承载文案生成或手势细节。

## 11. 验收标准

第一版完成后应满足：

1. 播放到配置的高光时间点时，弹幕输入按钮旁边出现一句待发送心里话；
2. 系统一次只展示一句草稿；
3. 草稿不遮挡人物主体、字幕、右侧操作栏、进度条和底部 tab；
4. 用户不操作时，草稿在展示时长结束后自然消失；
5. 用户轻推草稿达到阈值后，草稿被发送；
6. 推出动画能让用户感知草稿变成了弹幕；
7. 发送后的弹幕进入正常弹幕轨道，从右向左移动；
8. 未达到阈值时，草稿回弹，不发送；
9. 同一个 cue 完成或消失后不在同一轮播放中重复触发；
10. 不破坏视频播放、暂停、seek、竖滑切集、普通弹幕和 Story Q&A；
11. 前端 typecheck 和相关测试通过。

## 12. 非目标

第一版不做：

- 多个候选句；
- 换一句；
- 用户手动编辑草稿；
- 点击即发送；
- 投票；
- 情绪光场；
- 复杂弹幕墙管理；
- 服务端 schema 强制迁移；
- 满屏发送特效。

## 13. 后续扩展

如果第一版验证有效，后续可以探索：

- 由高光识别和 LLM 自动生成心里话弹幕；
- 根据不同高光类型生成不同语气模板；
- 将发送事件回传后端，用于评估文案命中率；
- 与情绪光场组合：先连点释放情绪，再给一句可发送心里话；
- 在答辩 debug 面板展示生成依据，例如字幕窗口、弹幕上下文和高光类型。
